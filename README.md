# rucc-cross

The toolchains, the environment and the C corpus that [rucc](https://github.com/tamnd/rucc) is compared against when it cross compiles. Zig 0.16, gcc, qemu, and the C that tells them apart.

There is no rucc code here. It moved. `rucc-tuple`, `rucc-abi`, the seventeen specification documents and the milestone issues all live in `tamnd/rucc`, in `crates/` and in `spec/cross-compile/`, because a crate the compiler depends on has no business being in a second repository and a version skew between the two is a bug waiting for a bad week. What is left here is the part that genuinely does not belong in a compiler checkout: a gigabyte of downloaded toolchains, an emulator per architecture, and the programs you run under them.

## What it is for

A cross compiler is a claim about a machine you are not standing next to. The only way to check one is to have something else compile the same source for the same machine and see whether the two agree, and then to run both and see whether they agree about that too. This repository is the something else.

Three things, and they are separable.

**The toolchains.** `toolchains/manifest` pins what we compare against, with a hash. `toolchains/install zig` fetches it and refuses anything whose hash does not match. Nothing is fetched from a URL that is not on a line somebody reviewed.

**The environment.** `targets` says how each of rucc's forty two targets is spelled to zig, to gcc, and to qemu. Every entry in the zig column was checked by running the compiler rather than read out of a manual, and the dashes are the ones that failed.

**The corpus.** `corpus/layout` is C that any correct compiler for a target must accept, written as assertions with the reason beside them. `corpus/abi` is C that has to produce the same output on every target, so a target that produces different output has miscounted a register rather than laid something out differently. `corpus/exec` is the smallest thing that proves a sysroot and a link line work at all.

**The sysroots.** `sysroots/manifest` pins the libc source with a hash, the same way the toolchains are pinned, and `bin/sysroot` builds one for a target and writes the record of what went into it. This is the producer that `rucc-sysroot` in the compiler repository deliberately does not contain, because fetching needs a cache, a provenance record and a network policy, and a crate the compiler links against should have none of those.

**The glibc headers.** `bin/glibc-headers` does for glibc what `bin/sysroot` does for musl, for the nine ABIs the target table has a glibc row for, and it produces one tree rather than nine: the headers every one of them installs identically go in the shared directory and the rest go in one directory per family, which is 411 shared against 77 distinct files in 453 copies. It installs headers only, so it is a minute and a half per row rather than a build, and it checks that the shared tree plus a family's tree is each of that family's installs byte for byte before it writes anything. `bin/glibc-distribution` is the check that the text is what a real distribution ships, file by file, and `sysroots/distribution-patches` names every file a distribution changed and what it changed. `bin/glibc-versions` answers the question the next tree has to answer, which is what the releases people target actually differ by: eight installs from 2.28 to 2.44, and a record of which of the 498 headers each release changed.

**The kernel headers.** `bin/kernel-headers` is the other half of a Linux sysroot. A libc's headers are not enough to compile a program: 31 of glibc's installed headers include `<asm/...>`, `<asm-generic/...>` or `<linux/...>` and 3 of musl's do, and those come from the kernel rather than from any libc. It runs `make headers_install` out of a pinned Linux source, once per architecture, and lays the result out as one shared directory plus one small directory per architecture, which is the pair the compiler searches after the libc's pair.

## Using it

```
toolchains/install zig          fetch the pinned reference compiler
bin/facts --all                 what the reference says about every target's scalar types
bin/facts --check               fail if anything in facts/ has drifted
bin/compile-corpus              compile the layout corpus for all forty two targets
bin/compile-abi-corpus          compile the compiler's generated layout corpus, one file per target
bin/compile-abi-signatures      compile the compiler's generated signature corpus, for every target
bin/run-corpus                  build and run the executing corpus, with the reference
bin/run-corpus --cc rucc        the same corpus and the same transcripts, built by rucc
bin/rucc-cc x86_64-linux-musl   run rucc against the sysroot produced for that target
bin/run-abi-signatures          build the signature corpus with the reference and run it under qemu
bin/sysroot aarch64-linux-musl  produce a musl sysroot, with a manifest
bin/kernel-headers              produce the Linux uapi headers every Linux target needs as well
bin/glibc-headers               produce glibc's headers for all nine glibc ABIs, as one tree
bin/glibc-distribution          hold those headers against a real distribution's own, file by file
bin/glibc-versions              record which releases changed which header, for the merge ahead
bin/abilist x86_64              extract glibc's own symbol list, for the compiler's stub comparison
bin/sysroot --check a b         compare two manifests, which is the reproducibility check
bin/lint                        the house rules
```

`bin/compile-abi-corpus` is the one that reads the other repository. It takes the directory `cargo xtask abi-corpus` writes, which defaults to `../rucc/tests/abi-corpus` and can be given as an argument or in `RUCC_ABI_CORPUS`, and compiles each file for the target it is named after. The difference from `bin/compile-corpus` is what the C is: that one is C somebody wrote here, this one is C the compiler generated, and every line of it is a `_Static_assert` about a size, an alignment or a member offset that came out of `rucc_types::layout_record`. So a failure is not a corpus that will not build, it is the compiler and the reference disagreeing about a record, and the assertion that failed names it.

`bin/compile-abi-signatures` reads the other repository too, and it answers a smaller question than its name suggests. The corpus it takes is one program in four files, written by `cargo xtask abi-signatures`, whose two halves are meant to be compiled by two different compilers and linked together so that a value arriving in the wrong register has somewhere to show up. Running it that way needs a back end and a way to execute the result, so the compiler repository does that on the one target it can. What happens here is that both halves are compiled for every row of the table, and all that says is that the corpus is C the reference accepts everywhere. That is worth a job on its own, because the corpus is generated and the grammar behind it grows, and a shape that is fine on x86-64 and a constraint violation on s390x should turn up the day it is added rather than the day somebody writes a back end. `report.c` is left out of it: it is the one file of the four that includes a libc header, and asking a freestanding row for `stdio.h` would fail for a reason that has nothing to do with the corpus.

`bin/run-abi-signatures` takes the same corpus and runs it. Both halves are built by the reference, which makes it the control build of the four the differential harness does rather than the differential itself, because the other three need rucc to emit code for the target and today it emits code for one. The control is worth running on every architecture anyway. A generated program is a program nobody read, and compiling it only catches the shapes the reference rejects: a value checked against the wrong promoted type, or a `long double` whose bit pattern differs between architectures, is a corpus bug that compiles fine everywhere and fails when it runs. Finding those here is much cheaper than finding them inside a differential where the answer is supposed to mean something about the compiler.

It is also how each architecture's emulator gets characterized, which is what the known divergence list in `spec/cross-compile/14-testing.md` section 14.4 is made of. Every instruction in the binary came from the reference, so a crash is qemu and nothing else, and the number of crashes retried is printed at the end rather than swallowed. It skips the same rows `bin/run-corpus` skips and for the same reasons, so the two cover the same set and a target cannot quietly appear in one and not the other.

`bin/run-corpus --cc rucc` is the other half of the comparison, and the first thing in this repository that runs the compiler rather than the reference. `bin/rucc-cc` is how: it wants `RUCC` pointing at a compiler, it wants a sysroot already produced for the row, and it gives rucc one cache directory and the target, because `rucc-sysroot` reads the same layout under the same name that `bin/sysroot` writes. Nothing else is passed, so a header that came from the machine instead of the sysroot would be a bug in the compiler's search path and not something this script arranged around. The reference stays the default, because a transcript recorded here has to come from something other than the compiler being tested before comparing anything against it means much.

It says why it skipped a row, and with `--cc rucc` two of the reasons are about the compiler: a row nobody has produced a sysroot for, and a row whose architecture has no back end yet, which is every row that is not x86-64. A static binary for the machine's own architecture and kernel runs on hardware rather than under qemu, which is how x86_64-linux-musl gets tested on an x86-64 Linux box with no emulator installed at all.

`bin/kernel-headers` produces the other half of a Linux sysroot, and it produces it once for the whole target table rather than once per target. `make headers_install` from the pinned Linux source is the supported way to get these headers and the only reproducible one, because copying `include/uapi` out of the source tree skips the pass that takes the kernel's own `__KERNEL__` sections out of every file. The layout is one rule: a header that every architecture installs with identical contents goes in the shared directory, and every other header goes in the directory of each architecture that has it, which the compiler searches first. On linux 6.19 that is 970 shared and 333 per architecture, 9.1 MB against 2.2 MB, so the alternative of a private copy per target would cost nine megabytes a row.

It needs a Linux host, and that is not a convenience. Eight of these headers differ from eight others only in case, all of them in netfilter, where the lowercase name is an iptables match and the uppercase one is a target, so on a default macOS filesystem one of each pair silently overwrites the other and the tree that comes out is missing eight headers and has eight others under names that are not theirs. The script checks for a case sensitive filesystem before it downloads anything and says that rather than producing that.

`bin/glibc-headers` is the libc half for the nine rows of the table that say gnu rather than musl, and it produces one tree for all nine the way `bin/kernel-headers` produces one tree for seven architectures. Nine installs rather than eight, because the tree a program reads is chosen by the size of a pointer and a long and not by the instruction set, so x86_64, i386 and x32 are three sets of types out of the same sysdeps directories. `make install-headers install-bootstrap-headers=yes` is the whole of it, which is a minute and a half per row against the twenty minutes a build would take, and the script runs three at a time. Seven trees come out of those nine installs, because a tree is per family and a family is coarser than an ABI: glibc's own headers read `__x86_64__` and `__ILP32__` and answer for all three x86 ABIs out of one text, which the nine installs are held against each other to check rather than taken on trust. The same one rule splits the result: 411 headers are identical across the families and go in the shared directory, 77 are not and go in the directory of each family that has them, which is 453 copies. The tree is 5.3 MB with 3.1 MB of that shared, 677 KB gzipped, against the 31 MB nine separate installs would cost.

Three configure cache variables are set on the way in, because glibc asks the compiler for `-fno-pic`, `-mlong-double-128` and `-mno-gnu-attribute` and clang has none of the three. All three questions are about building the library and a header install compiles nothing, but that is an argument rather than a measurement, so here is the measurement: seven of the nine rows were installed a second time with Ubuntu's own cross gcc for that architecture, with no overrides, and `diff -r` between the two trees is empty for every one of them. The two that cannot be checked that way are i686, where Ubuntu's i686-linux-gnu-gcc defines `__CET__` by default and glibc then refuses to configure for i386 at all, and loongarch64, which has no cross gcc in Ubuntu 24.04.

Two files in the tree are not glibc's text as glibc wrote it, and the manifest's source column says so on both. `features.h` loses its `#define __GLIBC_MINOR__`, because the compiler defines that one from the target, which is what lets one tree serve every 2.x release and is what zig does to the same line. `gnu/stubs.h` is glibc's own prologue with nothing appended: the real file lists the functions that exist and fail with `ENOSYS`, which comes out of a built library rather than out of the source, and `features.h` includes the file unconditionally, so a tree without one compiles nothing at all. What the empty list costs is written down in tamnd/rucc#941.

`bin/glibc-distribution` is the check that the text is right, which is a different question from the two `bin/glibc-headers` answers for itself. That one checks that the tree reassembles and that two hosts produce it identically, and both of those are our output compared against our output. This one installs upstream glibc for each ABI the machine has a distribution header tree for, at the version the machine's own libc is, and compares every installed file byte for byte against the copy the distribution built from the same release. A file that differs and is not named in `sysroots/distribution-patches` with the reason is a failure, with the diff printed. Section 8.4 of the compiler's sysroot specification asks for this comparison as a list of sizes and offsets, and identical text is the stronger statement: it covers every macro, every conditional and every type at once, because a header that is the same file cannot disagree about anything.

On Ubuntu 24.04, which is glibc 2.39, eight of the nine rows have a tree to compare against and all eight come out the distribution's own text. The three x86 rows install 474 files with 469 identical, aarch64, riscv64 and powerpc64 install 467 with 462, arm and s390x install 466 with 461, and the five that differ are the same five files in every one of the eight trees. All five are Ubuntu patches, named and explained in `sysroots/distribution-patches`, and the run takes about two minutes. What this validates is the recipe rather than the pinned tree: `install-bootstrap-headers=yes` is a shortcut around a full build, the cache variables that get past the probes it skips are ours, and the question worth asking about them is whether what comes out is what a distribution ships.

The version comes from the machine and not from the pin, because a comparison between two different releases of glibc says nothing, so `sysroots/manifest` has a row per glibc version and the first one is the pin. The compiler is the distribution's own gcc wherever there is one, which is the opposite of everywhere else here, because a glibc this old cannot be configured with clang at all, and the findings below say where it stops. Where gcc is missing or cannot configure a row, the pinned zig is tried with the cache variables that get past those probes, and the run says which compiler each row used.

`bin/glibc-versions` is about the tree we do not have yet. One release's headers are what we ship, so a target asking for glibc 2.28 is handed 2.44's text, and section 8.3 of the sysroot specification says the fix is one tree with the per release differences written as `#if __GLIBC_MINOR__ >= n` inside each file. The first thing that work needs is not a merge, it is a measurement, because a merge nobody has measured is a merge nobody can review. So this installs glibc's headers once per release in `sysroots/manifest`, eight of them from 2.28 to 2.44, and writes down for every header which releases have it and which releases changed it. `sysroots/glibc-version-changes` is that record, with no argument the command holds what it produces against the committed copy, and `--write` replaces it.

What counts as a change is the code and not the bytes, which is the opposite of the choice `bin/glibc-distribution` makes, and both are right for what they ask. Holding one install against another install of the same release is a question about text, so any difference counts. Asking what a merged tree would have to write a conditional for is a question about code, and glibc bumps a copyright year in every file every January, so 420 of the 498 headers differ somewhere between 2.28 and 2.44 and almost all of that is text the merge would simply take from the newest release. Each file is therefore compared with its comments taken out, its blank lines dropped and its runs of spaces collapsed, which is a state machine in awk that knows about a block comment spanning lines and about `"/*"` inside a string literal.

One ABI, and it is x86_64, because the question is which of glibc's own files change between releases and that is a fact about glibc's source rather than about a machine. What differs between ABIs is what `bin/glibc-headers` already measured and split into seven family trees, and eight releases times nine ABIs would be seventy two installs for an answer the ninth would not change. The compiler is the distribution's own gcc with the pinned zig as a fallback, the same order and for the same reason as `bin/glibc-distribution`, and a run on a warm cache takes eleven seconds because the installs are kept.

`bin/abilist` fetches the pinned glibc source and takes one kind of file out of it: the abilist, which is glibc's own record of which symbol it exports at which version node, one file per architecture. That is the description the compiler writes its glibc stubs from, and `cargo xtask real-libc` over there writes a stub from it and holds it against the real `libc.so.6` on the machine, which `spec/cross-compile/09-libc-stubs.md` section 9.8 calls the highest value test in that document. The rule it checks is that the real library's symbols are a superset of ours, at the same versions, with the same sizes where there is storage to copy.

It is here rather than there for the reason `bin/sysroot` is: a comparison against a real libc needs a real libc's description, the description is twenty megabytes of tarball away, and a compiler checkout should not be downloading a libc to run its own tests. Nothing is copied into this repository either, because an abilist is part of glibc and carries glibc's licence, and a pinned fetch into the cache avoids the question entirely. The nightly run does it on both host architectures, which is two real libcs, and two more than any amount of reading our own output gives.

Set `RUCC_CROSS_REFERENCE=gcc` to compare against the platform's cross gcc instead of zig, for the rows where one exists. That column is much sparser than the zig one and the sparseness is the argument for this whole line of work: a per target gcc has to exist as a package before you can compare against it, and for most of the table nobody has built one.

The download cache is `$RUCC_CROSS_CACHE`, which defaults to `~/.cache/rucc-cross`. It is outside the checkout on purpose, so switching branches does not throw away a gigabyte.

## What it has found so far

The corpus earns its keep by being wrong in public, and so does producing a sysroot by hand. Twenty things, each of which was a plausible belief until something here said otherwise.

**Plain `char` is unsigned on s390x.** It was written down as signed, in with x86. The s390x ELF ABI says unsigned, and clang agrees, and the target had never been compiled for.

**mingw-w64 has an eighty bit `long double` and MSVC does not.** The rule was keyed on the operating system, so `x86_64-windows-gnu` got the eight byte answer that only `x86_64-windows-msvc` deserves. Two targets, one OS, different types.

**Windows on i386 aligns a `double` to eight and System V aligns it to four.** `__i386__` is not the condition. `__i386__ && !_WIN32` is. A struct of an int and a double is twelve bytes under one and sixteen under the other.

**s390x caps scalar alignment at eight.** An IEEE quad `long double` is sixteen bytes and aligned to eight there, and `__int128` is the same. It is the one target in the table where the size and the alignment of a scalar come apart in that direction.

**`__int128` is not a 64-bit only type.** wasm32 has it and so does `x86_64-linux-gnux32`, both with four byte pointers, which is a useful reminder that the pointer width and the widest integer are separate facts.

**wasm32 has a sixteen byte IEEE quad `long double`.** `rucc-abi` grouped it with 32-bit ARM on the reasoning that a machine with four byte pointers has nothing wider than a `double`, and `facts/wasm32-none.facts` had recorded quad and sixteen from the first day. The fact was on disk and the rule contradicted it, which is the case a recorded fact cannot catch on its own and the generated record corpus does, because the corpus asks the compiler for a struct rather than asking it for a list of sizes.

**The Linux uapi headers cannot be unpacked on a default macOS filesystem, and zig 0.16 ships without the eight that collide.** Eight pairs of them differ only in case: `xt_connmark.h` and `xt_CONNMARK.h`, and the same for `xt_dscp.h`, `xt_mark.h`, `xt_rateest.h`, `xt_tcpmss.h`, `ipt_ecn.h`, `ipt_ttl.h` and `ip6t_hl.h`. The lowercase one is an iptables match and the uppercase one is the target of the same name, and each uppercase file is a three line wrapper that includes its lowercase twin, so what a missing one costs is the file rather than any definition. Unpacking the tree on a case insensitive volume keeps one of each pair and gives it the other's contents, with no error from `tar`. The pinned zig tarball has all eight uppercase files missing and the eight lowercase ones present, on a Linux box as well as here, which is what that accident looks like once it has been shipped: `zig cc` for any Linux target cannot compile a program that includes `<linux/netfilter/xt_CONNMARK.h>`, and iptables includes it. `bin/kernel-headers` checks the filesystem before it downloads anything and refuses rather than producing a tree with that in it, which is why producing this tree is a Linux job.

**zig cc adds an argument to every command and then warns that it is unused, which breaks any probe using -Werror.** It passes `-c` to clang itself, so a command that was `-Werror -S` gets both, clang reports `-c` as an unused command line argument, `-Werror` turns that into an error, and the compilation fails with no diagnostic about the program. glibc's configure probes the alias attribute exactly that way, so the first thing this compiler says about glibc 2.44 is that it has no working alias attribute, about a compiler whose alias attribute works. `-Wno-unused-command-line-argument` in the wrapper is the fix and it costs nothing, but the shape of this is worth remembering: a compiler driver that edits the command line can make a correct probe give a wrong answer, and every autoconf script in the world is probes.

**zig cc will not compile anything with -fno-pic for a Linux target.** It answers "the selected target requires position independent code" for x86_64-linux-gnu, with `-static`, with `-fno-pie`, with any combination of the two. Real toolchains for that target do support it and glibc's configure uses it to ask whether the compiler reaches extern data through the GOT, so the option being refused outright rather than ignored is what stops that probe. It is a deliberate restriction rather than a missing feature, and it means a build system that uses `-fno-pic` to ask a question gets an error instead of an answer.

**Ubuntu's i686 cross gcc cannot configure glibc for i386, and the reason is a default.** `i686-linux-gnu-gcc` on 24.04 defines `__CET__` as 3 with no flags given, glibc 2.44's configure sees control flow protection enabled and stops with "CET is only supported on x86_64 or x32", and there is no way through it short of turning the default off. So the one row of nine that a Debian packaged compiler cannot be used to cross check is a 32-bit x86 row, which is the row most likely to have something wrong with it.

**There is no loongarch64 cross gcc in Ubuntu 24.04.** Not a missing package name, not a different prefix: the archive has cross compilers for aarch64, arm, riscv64, powerpc64, powerpc64le, s390x, mips and more, and nothing for loongarch64. It is the newest architecture in the table and the clearest case for what this repository is about, because a comparison against a per target gcc needs somebody to have packaged one first.

**One x86 header tree really does serve x86_64, i386 and x32, and the headers are where the branch is.** The three installs of glibc 2.44 are byte identical to each other, `diff -r` over each pair is empty, so there is one text and three sets of types out of it. `bits/wordsize.h` reads `__x86_64__` and `__ILP32__` and answers 64, 32 and 32 from the same file, which is what compiling for the three ABIs against the one tree prints back. riscv goes further and defines `__WORDSIZE` as `__riscv_xlen`, which is the compiler's own macro, so that family would serve a 32-bit port without a line changing. So the split is over the seven families the compiler searches for and not over the nine ABIs that get installed, and the nine installs are what checks the claim rather than what is shipped.

**A glibc as old as the one on a current Ubuntu cannot be configured with clang, and the pinned one can.** glibc 2.39 stops three times over. First on its own minimum compiler version check, because clang says `__GNUC__` 4.2 whatever it is. Then on a probe asking whether a builtin can be redirected with `__asm`, which clang does not support. Those two are cache variables and can be answered. The three after them are not: configure for aarch64 wants the SVE ACLE that glibc's mathvec code is written against, for powerpc64 it wants IBM 128-bit long double, and for s390x it wants `__builtin_tbegin`, and a missing feature has no cache variable. So the comparison against a distribution uses the distribution's own cross gcc for those rows and glibc 2.44 installs from zig for all nine, which is the reverse of the direction anybody would guess: the hermetic pinned compiler is the one that works on current sources, and the platform compiler is the one that works on old ones.

**Ubuntu patches five glibc headers, and the same five turn up in all eight architecture trees it ships.** `assert.h` gets a guard so a second include does not repeat its declarations, `elf.h` gets `AT_HWCAP3` and `AT_HWCAP4` backported from a later release, `features.h` loses the warning that `_FORTIFY_SOURCE` needs optimization, `paths.h` points `_PATH_VARDB` at `/var/lib/misc` where Debian policy puts it, and `stdbit.h` prefers the compiler's `__builtin_stdc_` functions to the library's own macros. Two things follow. A claim that our headers are the distribution's headers needs an allow list with a reason per file, not a count, which is what `sysroots/distribution-patches` is. And this is what a distribution patch looks like from the outside: it is applied to the source once and then appears in every architecture's install, so five files and eight trees is one decision and not eight.

**Debian multiarch is a fifth spelling of a machine, and i686's is i386-linux-gnu.** The target table already holds four: rucc's tuple, zig's, the gcc prefix and the qemu binary. The name a distribution uses inside a header tree is another one, it is what `/usr/include/<multiarch>` is, and it cannot be derived from the gcc prefix, because `i686-linux-gnu-gcc` prints `i386-linux-gnu`. So it gets asked for with `-print-multiarch` rather than computed. It matters for more than one directory name: `finclude/math-vector-fortran.h` is shipped at `finclude/<multiarch>/math-vector-fortran.h` in every one of those trees, so a file can be present under a path that upstream never writes, and a comparison that looks in one place concludes it is missing.

**Most of the difference between two glibc releases' headers is a copyright year.** 420 of the 498 headers in the range 2.28 to 2.44 are not the same bytes in every release they appear in, which reads like a merge with four hundred files to conditionalize. Strip the comments and it is 210. Two changes account for nearly all of the gap: the copyright line moves every January, and in 2019 the licence notice in every file changed `http://www.gnu.org/licenses/` to `https`. The pair 2.35 to 2.36 is the one that gives it away, because those two releases are from the same year and it is the one step where the byte count and the code count are almost the same number.

**Two hundred and twenty one of glibc's headers are the same code in all eight releases, and six of them change in every one.** 288 files never change the code in them at all and 221 of those are present from 2.28 through 2.44, so nearly half the tree needs no conditional written into it ever. At the other end, `bits/syscall.h`, `elf.h`, `features.h`, `stdio.h`, `stdlib.h` and `sys/cdefs.h` change at every one of the seven steps, and 94 of the 210 files that change at all are in `bits/`, which is also the part that differs per family. 81 files arrive after 2.28 and 17 are gone before 2.44, `crypt.h` and `sys/sysctl.h` and the inline maths headers among them, so the merge has to express a file's absence as well as its contents.

**glibc 2.17 will not configure on a current machine, and the reason is its own version check.** It reads the version of gcc and of make with a pattern that does not understand a two digit major, so with gcc 13 and make 4.3 on the path its configure stops saying both are missing or too old. 2.17 is the practical floor the stub document names, which makes this a real limit rather than a curiosity: a survey or a sysroot for that release needs either a compiler from that era or a patch to glibc's own configure, and 2.28 is the oldest release that just works, which is the release the same document calls the comfortable floor.

**A libc's headers are not enough to compile the libc's own headers.** `sys/soundcard.h` from the musl sysroot this repository produced does not compile without the kernel tree, because musl's `bits/soundcard.h` includes `<linux/soundcard.h>`. Three of musl's headers reach into the kernel's and thirty one of glibc's do, so the kernel tree is not an extra for programs that make system calls directly, it is part of what a Linux sysroot means. With it in place, a program including `<linux/version.h>`, `<asm/unistd.h>`, `<sys/ioctl.h>`, `<net/ethernet.h>` and `<sys/quota.h>` compiles for x86_64-linux-musl with every header coming from this repository's output and none from the machine.

**A sysroot built on a mac and a sysroot built on a Linux box were different files with identical instructions.** The 219 headers matched on the first try and the six compiled artifacts did not, because clang writes the working directory into `DW_AT_comp_dir` of every object it produces, including the ones assembled from `.s` files, and `/Users/apple/...` is not `/home/tam/...`. `bin/sysroot` passes `-fdebug-compilation-dir=.` and `-ffile-prefix-map` for that reason, and with them all four musl targets reproduce byte for byte across the two hosts.

The first two and the sixth were bugs in `rucc-tuple` and `rucc-abi` and all three are fixed. The middle three were bugs in this corpus, and the comments in `corpus/layout/scalars.c` say so where they happened. The last one is why `bin/sysroot` has two flags in it that look like noise and are not.

## Layout

```
targets              how each rucc target is spelled to each tool, and what runs a binary for it
toolchains/manifest  what we compare against, pinned with a hash
toolchains/install   fetch and verify
sysroots/manifest    the libc sources a sysroot or an abilist comes from, pinned the same way
sysroots/distribution-patches  the headers a distribution changed, and what it changed in each
sysroots/glibc-version-changes  which releases changed which header, for the merge that has to know
bin/                 the drivers, all POSIX sh
corpus/layout        C that has to compile, with the reason for each assertion beside it
corpus/abi           C that has to produce the same output everywhere
corpus/exec          the smallest thing that proves a sysroot works
facts/               what the reference says about each target, recorded and checked in CI
```

Everything is POSIX sh. There is no build system and no dependency file, and that is deliberate: the day this repository needs a language with a build system is the day somebody should ask whether the thing being built belongs in `tamnd/rucc` instead.

## Where the design is written down

`spec/cross-compile/` in the compiler repository, starting at [`00-README.md`](https://github.com/tamnd/rucc/blob/main/spec/cross-compile/00-README.md). Section 14 is the testing document and it is the one this repository implements. The tracking issue is [tamnd/rucc#618](https://github.com/tamnd/rucc/issues/618).
