# Changelog

The format is a section per change, newest first, written by hand. There are no releases and no version numbers, because there is nothing here to install. What a user of this repository consumes is the checkout itself, so the dates are the interesting axis and a tag would only be a second name for a commit.

## Unreleased

`bin/glibc-startfiles` builds `libc_nonshared.a` as well, for all nine glibc ABIs, and links it. That archive is the other half of what a link line needs and the reason is not a detail of packaging: it holds the functions glibc compiles into every program rather than into the shared library, and `libc.so.6` exports none of them, so a sysroot with the eight start files and no archive links a hello world and stops at the first `atexit`. Four members are on every ABI, `atexit`, `at_quick_exit`, `pthread_atfork` and `__stack_chk_fail_local`, and they cost 51 KB across the nine ABIs against the 130 KB the start files are. With this, validation 3 of section 8.4 of the compiler's sysroot specification has a link line it can actually use for a program that calls something, which is what box 7 of tamnd/rucc#926 is about.

Nothing in glibc builds one member on its own. The archive's own rule collects a stamp file from every subdirectory, which is the full twenty minute build, so each member is compiled by asking its subdirectory for that one object and the nine archives are made with zig's `ar`, whose output has no timestamps, uids or modes in it and is the same bytes every time. The member list stays glibc's rather than becoming ours: every subdirectory named in the configured build's `sysd-sorted` is asked what its `static-only-routines` variable expands to, which is where glibc keeps exactly this answer, and a release that moves a routine or adds one is then something this notices rather than a member that quietly stops being produced. Fifty subdirectories at eighty milliseconds of read phase each is seven seconds per ABI, and the whole run is four minutes for all nine.

Two link shapes come with it, because the archive is not checked by being hashed. The first is a PIE that links the archive and touches all four members, with `atexit` the one that has an observable answer: `main` returns 7 and the handler it registered exits 0, so the process says 0 only if the handler ran. The second is the same program under `-pg` with `gcrt1.o`, run in a directory of its own, which has to leave a `gmon.out` behind. That file is written by `_mcleanup`, which the profiling start file registers with `atexit`, so a `gmon.out` is the profiler saying it reached our archive and ran what it found there. Both shapes link on eight of the nine ABIs and run on seven, on hardware for the host's own row and under qemu for the rest, with loongarch64 having no cross gcc on the machine and x32 having nothing that can run it. The member lists are also held against the distribution's own `libc_nonshared.a` for each ABI that has one, and all eight are the same set, which is the check that the sweep above did not miss a subdirectory.

**`libc.so.6` exports none of the four functions in `libc_nonshared.a`.** Ubuntu 24.04's x86-64 `libc.so.6` has no `atexit`, no `at_quick_exit`, no `pthread_atfork` and no `__stack_chk_fail_local` in its dynamic symbol table, which is the measurement that makes the archive a requirement rather than a nicety. `atexit` is the one to reason from, because it is in every C program that registers a cleanup and in every program built with a C++ runtime, and what resolves it is a static member of this archive that calls `__cxa_atexit` in the shared library with the caller's own `__dso_handle`. That is also why the archive cannot be replaced by a symlink or a linker script: the member exists so that each object gets the handle of the thing it was linked into.

**glibc's list of what goes in the archive is per subdirectory and per architecture, and `make` will not print it.** `make -p -q` prints a recursive variable as it was written rather than as it expands, and on arm `static-only-routines` is written as `$(aeabi_constants) aeabi_read_tp`, so what comes back is that text and not the four names it stands for. A second makefile with one rule that echoes the variable goes through make's own expansion instead, and on arm the answer is eight members rather than four: `sysdeps/arm` adds the aeabi helpers to the `csu` directory's list, and Debian's armhf `libc_nonshared.a` has exactly those eight. An architecture can add to this archive, so a list written down here would have been a list that is wrong for one row in nine.

**A subdirectory's read phase prints other people's recipes.** Asking `iconvdata` for a variable prints six lines that have nothing to do with the question, because its makefile includes a generated rules file, make has to build that file before it can finish reading, and the recipes it runs to build it echo as they go. Taking the first line of output is then taking a path out of somebody else's recipe and trying to compile it, which is what the first run of this did. The answer is marked with a word of its own and picked out by that mark, and the shape generalizes past make: reading a tool's answer off the top of its output assumes the tool said nothing else, and a tool that rebuilds something as a side effect of being asked always says something else.

**`csu` has to be built before `nptl`, and the dependency is a generated header.** `pthread_atfork` compiles in the `nptl` directory and includes `internaltypes.h`, which includes `sem_t-align.h`, which is generated, and the directory that generates it is `csu`, because that is where glibc's `gen-as-const-headers` list names it. A run that asked `nptl` first stops on a header nothing has written yet. So the order in the script is the `csu` recursion and then the member sweep, and that is a requirement rather than a preference: a build that fans the subdirectories out in parallel would be racing for that header.

**`-nostartfiles` drops gcc's `crtbegin` too, and the archive's `atexit` needs it.** The flag is about the start file, but in gcc's spec the start file and `crtbegin.o` are in the same part of the line, so turning it off removes both, and a link of our `atexit` then stops on an undefined `__dso_handle`, which is `crtbegin`'s symbol. Asking the compiler for the file by name with `-print-file-name=crtbeginS.o` and putting it on the line is what the real link does anyway in the part that was turned off. It also has to be the `S` suffixed pair for position independent code and the plain pair for `-no-pie`, which is the same choice gcc's own spec makes a line further down.

**Nothing selects `Mcrt1.o`.** It is the start file for `-p`, and Ubuntu's gcc answers `-p`, `-pg` and `-profile` with `gcrt1.o` for all three, so a link that used `Mcrt1.o` would be a link no compiler performs. It is produced, because glibc installs it and every ABI has to install the same list, and it is identity checked, and it is not linked, which leaves the profiling coverage where it belongs: on the file a profiling build actually gets.

`bin/lint` checks that the rows of one source in `sysroots/manifest` are in descending version order. The header of that file already says the first row of a source is the pin and every later one is a release fetched for a comparison, and nothing enforced it, so a new release appended at the bottom the way a row of any other file would be left the pin where it was. That is the quiet failure rather than a loud one: the tree we ship and the stubs we generate stay on the old release, every command still works, and the only sign is that the new release turns up in the comparison runs and nowhere else. The check is per source rather than over the whole file, so a second musl or Linux row is held to the same rule, and two rows of one source with the same version are caught too, since a duplicate is the other way to write the same mistake.

`bin/glibc-startfiles` builds glibc's start files for all nine glibc ABIs, with the pinned zig and the pinned source, and then links and runs them. These are the eight objects a Linux link line begins with before anything of the program's own: `crt1.o` for a non PIE executable, `Scrt1.o` for the PIE that is everybody's default now, `rcrt1.o` for a static PIE, `crti.o` and `crtn.o` around the init and fini sections, and `Mcrt1.o`, `gcrt1.o` and `grcrt1.o` for profiling. Everything else here either installs a libc's text or reads it, so this is the first thing in the repository that compiles part of a libc, and it is the step box 7 of tamnd/rucc#926 is waiting on: the validation it asks for is running a program built against our tree, and nothing could be linked at all while the glibc side was headers only.

A full build of glibc is twenty minutes an ABI and these eight files are thirty seconds, so the eight come first. There is no make target for one of them, though. `make csu/crt1.o` in a configured build directory is not a rule glibc has, and what works is glibc's own recursion into the directory: `make -r -C $source/csu ..=../ objdir=$build install_root=$install install-lib-nosubdir` builds and installs exactly the list glibc itself would have installed. Three ABIs run at a time, so all nine take about a minute and a half, and the files land in one directory per ABI rather than per family, which is the opposite of the header tree's layout and right for the same reason the headers' layout is right: a header can ask the compiler what machine it is on, and an object cannot.

Four checks run before anything is written. Every object's ELF header is read back with `od`, which is in POSIX where `readelf` is not on a mac, and held against the class, byte order, type and machine the row says it should have, and two rows make that worth having on its own: x32 is a 32-bit object claiming machine 62, and s390x is the one big endian row. Every ABI has to have installed the same eight names, so a row that quietly produced seven fails rather than shipping. Then the check program is linked three ways against each ABI's files and run, with `Scrt1.o` alone, `Scrt1.o` between `crti.o` and `crtn.o`, and `-no-pie crt1.o` the same way. The program has a constructor, a destructor and a look at `argc`, `argv` and `envp`, so a start file that did not hand the program a stack fails rather than exiting 0 by luck. Eight of the nine ABIs run, on hardware for the host's own row and under qemu for the others, loongarch64 links nowhere because Ubuntu has no cross gcc for it, and x32 is linked and never run for a reason below. The other four files are produced and identity checked and not linked: a static PIE needs a static glibc that does not exist yet, and the profiling three pull `atexit` out of `libc_nonshared.a`, which is the next thing to build and the reason tamnd/rucc#941 is still open.

The link is done by the distribution's cross gcc rather than by zig, and that is a finding and not a preference. All 72 objects are byte identical across two builds from two unpacked copies of the same source in different directories, and the nightly run produces them on an x86-64 host and an aarch64 host and holds the two manifests against each other, the same criterion as the two header trees and the same reason for running twice. It fails the run like they do, twice over: an object that came out different on two hosts is the same bug as a header that did, and one that does not link or does not run is a worse one.

**zig cc writes the dependency file and nothing else when `-S` is on the same line.** glibc's generated constants rule runs `cc -S -o x.s -MD -MP -MF x.d -MT x.s -x c -` with the program on stdin. zig handles the four dependency options itself rather than handing them to clang, writes `x.d`, writes no assembly at all and exits 0, so make records a success and the script that reads `x.s` next dies with a file not found. Running the line twice, once as given and once with those four options removed, is the fix, and materializing stdin into a file first is what lets it run twice. That leaves a second thing to undo, because the dependency file then names a temporary that is about to be deleted, and make restarts when a dependency file it included has changed, so the pass after that stops on a prerequisite nothing can build. Taking the name back out is what gcc does with the same command anyway: given a program on standard input it writes down the headers it read and nothing at all for the source. The shape generalizes past this one rule: a driver that consumes an option instead of passing it on can turn one command into a different command, and exit 0 is not a claim that the work got done.

**zig cc tells a cross build where the host's gcc keeps its headers.** `zig cc -print-file-name=include` answers `/usr/lib/gcc/x86_64-linux-gnu/16/include`, because clang looks for an installed GCC for the target and finds the machine's. glibc's configure asks exactly that and puts the answer in `SYSINCLUDES`, so a build of glibc's own files with a hermetic pinned compiler compiles them against the host gcc's `stddef.h` unless that variable is overridden on the make line, which is what this does. Nothing warns and the objects still come out, which is the host contamination section 8.5 of the sysroot specification exists for. A hermetic compiler is not the same thing as a hermetic build.

**zig cc rejects an input by its suffix and an option by not knowing it, and glibc needs both.** Three of the eight files are a relocatable link of an object glibc names `.os`, and zig answers "unrecognized file extension", because its driver decides what an input is from the name. And glibc will not configure powerpc64le or s390x unless the compiler takes `-mlong-double-128` and `-mno-gnu-attribute`, which zig stops on with "Unknown Clang option", and answering the two probes no does not help, because configure puts the missing option in `critic_missing` and refuses the row instead. So the compiler wrapper copies the file to a `.o` and drops the two options, which is the difference between seven ABIs and nine, and neither rewrite can reach the output: clang has only ever had the 128-bit long double ABI on those two machines, and it does not write the `.gnu_attribute` directives the other option turns off.

**zig cc links its own crt1.o for a glibc target even with -nostartfiles.** A link against the start files it has just produced fails on a duplicate `__data_start` and `_IO_stdin_used`, and no flag gets ours used instead. The link and run check therefore uses the distribution's cross gcc, which is the better tool for the job anyway, because the package that provides it is also what puts the target's loader and shared libc on the disk, and that is what makes running the result under qemu possible at all. `zig cc` is a compiler for zig's own sysroot, and `-nostartfiles` there is a statement about zig's start files rather than about the target's.

**clang writes debug information for an assembly file nobody asked to debug, and that is what made two hosts disagree.** For a `.S` input with no `-g` given it still emits `.debug_info`, `.debug_line`, `.debug_aranges` and `.debug_ranges`, with the source directory sitting in `DW_AT_comp_dir`, and glibc's own `CFLAGS` have a `-g` in them anyway. `-g0` last on the command line, where it beats what the build system put earlier, is the whole of the fix, and it has to happen at compile time, because `zig objcopy --strip-debug` refuses a relocatable object with "ELF to ELF copying only supports programs" and there is no stripping it afterwards with the pinned tools. With it, `crt1.o` is 2216 bytes instead of 5736, against the 2120 of the distribution's stripped one.

**glibc's start files are the distribution's own, and two build flags are the whole difference.** Built from 2.39, which is Ubuntu 24.04's release, and held against the objects in the distribution's `libc6-dev` after `objcopy --strip-debug -R .comment`, six of the eight match byte for byte. Configure with `--enable-stack-protector=strong` and seven do. Compile with `-fno-omit-frame-pointer`, which is Ubuntu's distribution wide default rather than anything glibc asks for, and all eight do, the last holdout being `gcrt1.o` differing by a frame pointer prologue. So the csu recursion produces the real thing rather than something that resembles it, and what is left over is somebody's packaging decision and not our recipe.

**Nothing on a Linux host runs an x32 binary.** The target table said `qemu-x86_64` for that row and that is wrong twice over: qemu 8.2.2 installs fifty user mode emulators and not one of them is an x32 one, so `qemu-x86_64` takes the file and says "Invalid ELF image for this architecture", and Ubuntu 24.04's kernel ships `CONFIG_X86_X32_ABI` unset, so running it directly is an exec format error. The entry had never been exercised, because everything here that runs something skips a glibc row whose loader is not on the machine, and it sat in the table until the first x32 binary was linked and tried. The row now says a dash, with the measurement written above the table, and the ABI is still compiled and linked for everywhere it was before.

`bin/glibc-versions` records what glibc's installed headers actually differ by between the releases people target. Section 8.3 of the compiler's sysroot specification wants one header tree per libc with the per release differences written as `#if __GLIBC_MINOR__ >= n` inside each file, which is how one tree serves every 2.x release. We ship one release's headers today, so a target asking for 2.28 is handed 2.44's text, and the first thing the merge needs is not a merge, it is a measurement: a merge nobody has measured is a merge nobody can review. So this installs glibc's headers once per release in `sysroots/manifest` and writes down, for every header, which releases have it and which releases changed it. `sysroots/glibc-version-changes` is that record, 498 rows, and with no argument the command holds what it produces against the committed copy.

Six glibc rows join the manifest, so there are eight from 2.28 to 2.44, and each one is a distribution somebody targets: 2.28 is RHEL 8 and Debian 10, 2.31 is Ubuntu 20.04, 2.34 is RHEL 9 and the release that merged libpthread into libc, 2.35 is Ubuntu 22.04, 2.36 is Debian 12, 2.39 is Ubuntu 24.04, 2.41 is Ubuntu 25.04, and 2.44 is the pin. The set of rows is the survey's version list on purpose, because a second list of releases somewhere else is a second thing to forget.

What counts as a change here is the code and not the bytes, which is the opposite of the choice `bin/glibc-distribution` makes, and each is right for the question it asks. Holding one install against another install of the same release is a question about text, so any difference counts. Asking what a merged tree would have to write a conditional for is a question about code. Each file is therefore compared with its comments taken out, its blank lines dropped and its runs of spaces and tabs collapsed, which is a state machine in awk that knows about a block comment spanning lines and about `"/*"` inside a string literal. One ABI, and it is x86_64, because what differs between ABIs is what `bin/glibc-headers` already measured and split into seven family trees, and eight releases times nine ABIs is seventy two installs for an answer the ninth would not change.

**Most of the difference between two glibc releases' headers is a copyright year.** 420 of the 498 headers in the range are not the same bytes in every release they appear in, which reads like a merge with four hundred files to conditionalize. Strip the comments and it is 210. Two changes account for nearly all of the gap: the copyright line moves every January, and in 2019 the licence notice in every file changed `http://www.gnu.org/licenses/` to `https`. The step from 2.35 to 2.36 is the one that gives it away, because those two releases are from the same year and it is the one step where the byte count and the code count are nearly the same number.

**Two hundred and twenty one of glibc's headers are the same code in all eight releases, and six of them change in every one.** 288 files never change the code in them at all, and 221 of those are present from 2.28 through 2.44, so nearly half the tree needs no conditional written into it ever. At the other end, `bits/syscall.h`, `elf.h`, `features.h`, `stdio.h`, `stdlib.h` and `sys/cdefs.h` change at every one of the seven steps, and 94 of the 210 files that change at all are in `bits/`, which is also the part that differs per family. 81 files arrive after 2.28 and 17 are gone before 2.44, `crypt.h` and `sys/sysctl.h` and the inline maths headers among them, so a merged tree has to be able to say that a file is absent as well as what is in it.

**glibc 2.17 will not configure on a current machine, and the reason is its own version check.** It reads the version of gcc and of make with a pattern that does not understand a two digit major, so with gcc 13 and make 4.3 on the path its configure stops saying both are missing or too old. 2.17 is the practical floor that `spec/cross-compile/09-libc-stubs.md` section 9.5 names, which makes this a real limit rather than a curiosity: a survey or a sysroot for that release needs either a compiler from that era or a patch to glibc's own configure. 2.28 is the oldest release that just works, and it is the one the same section calls the comfortable floor, so that is where the survey starts.

The nightly run holds the record against what the runner produces, on one host rather than two, because the survey installs one ABI and the other runner would produce the same record. It fails the run like the other header jobs: a record that has stopped describing what comes out is a record nobody should be reading. A run on a warm cache is eleven seconds, because the installs are kept in the cache rather than thrown away.

`bin/glibc-distribution` holds upstream glibc's installed headers against a real distribution's own, file by file, at the version that distribution ships. Section 8.4 of the compiler's sysroot specification asks for this comparison as a list of sizes and offsets, and a byte comparison is the stronger form of the same question: identical text covers every macro, every conditional and every type at once, because a header that is the same file cannot disagree about anything. What it cannot do is say that a difference does not matter, so every file that differs has to be named with the reason instead of counted, which is what `sysroots/distribution-patches` is for.

It is a separate command from the producer rather than a flag on it, because the version has to come from the machine and not from the pin. The pin is the newest release and a distribution ships an older one, and a comparison between two different releases of glibc says nothing at all, so `sysroots/manifest` now has a row per glibc version with the first one being the pin, and a glibc 2.39 row beside the 2.44 one. What this validates is the recipe and not the pinned tree: `install-headers` with `install-bootstrap-headers=yes` is a shortcut around a full build, the cache variables that get past the probes it skips are ours, and the question worth asking about both is whether what comes out is the text a distribution ships. The pinned tree has the other two checks, that it reassembles and that two hosts produce it identically, and neither of those compares our output against anybody else's.

On Ubuntu 24.04, which is glibc 2.39, eight of the nine rows have a distribution header tree to compare against and all eight come out the distribution's own text. The three x86 rows install 474 files with 469 identical, aarch64, riscv64 and powerpc64 install 467 with 462, arm and s390x install 466 with 461, and the five that differ are the same five files in all eight trees. loongarch64 is skipped, because Ubuntu ships no tree for it, and a skipped row says so rather than failing. The whole run is about two minutes. The failure path was tested by taking one line out of `sysroots/distribution-patches`, which named the file, printed the two line diff of `_PATH_VARDB` and exited 1.

**A glibc as old as the one on a current Ubuntu cannot be configured with clang, and the pinned one can.** glibc 2.39 stops three times over. First on its own minimum compiler version check, because clang says `__GNUC__` 4.2 whatever it is, and then on a probe asking whether a builtin can be redirected with `__asm`, which clang does not support. Both of those are cache variables and can be answered. The three after them are not: configure for aarch64 wants the SVE ACLE that glibc's mathvec code is written against, for powerpc64 it wants IBM 128-bit long double, and for s390x it wants `__builtin_tbegin`, and a missing feature has no cache variable. So this comparison uses the distribution's own cross gcc where there is one and the pinned zig where there is not, and it says which compiler each row used, while glibc 2.44 installs from zig for all nine rows. That is the reverse of the direction anybody would guess: the hermetic pinned compiler is the one that works on current sources and the platform compiler is the one that works on old ones.

**Ubuntu patches five glibc headers, and the same five turn up in all eight architecture trees it ships.** `assert.h` gets a guard so a second include does not repeat its declarations, `elf.h` gets `AT_HWCAP3` and `AT_HWCAP4` backported from a later release, `features.h` loses the warning that `_FORTIFY_SOURCE` needs optimization, which its own default would otherwise print on every unoptimized compile, `paths.h` points `_PATH_VARDB` at `/var/lib/misc` where Debian policy puts it rather than at `/var/db`, and `stdbit.h` prefers the compiler's `__builtin_stdc_` functions to the library's own macros. Two things follow from that. A claim that our headers are a distribution's headers needs an allow list with a reason per file rather than a count, which is the new data file. And this is what a distribution patch looks like from the outside: applied to the source once and then present in every architecture's install, so five files across eight trees is one decision and not eight.

**Debian multiarch is a fifth spelling of a machine, and i686's is i386-linux-gnu.** The target table already carries four of them, rucc's tuple, zig's, the gcc prefix and the qemu binary, and the name a distribution uses inside a header tree is another. It is what `/usr/include/<multiarch>` is, and it cannot be derived from the gcc prefix, because `i686-linux-gnu-gcc -print-multiarch` prints `i386-linux-gnu`. So it is asked for rather than computed. It matters for more than a directory name: `finclude/math-vector-fortran.h` is shipped at `finclude/<multiarch>/math-vector-fortran.h` in every one of these trees, so a file can be present under a path upstream never writes, and a comparison that looks in one place concludes it is missing. Three places get looked in for that reason.

The nightly run does it on an x86-64 host and an aarch64 host, and it is one of the jobs that fail the run. A header that is not the distribution's text is either a patch nobody has written down yet or a recipe that has stopped producing what it claims to, and both are somebody here reading a diff. The x86-64 runner compares eight rows and the aarch64 one compares six, because the two extra x86 ABIs need `gcc-i686-linux-gnu` and `gcc-x86-64-linux-gnux32`, which Ubuntu packages for an amd64 host only, and `toolchains/install gcc-cross-x86` is the new name for that pair. What is wanted from those two packages is not the compiler but the `libc6-dev-*-cross` each one pulls in, which is the distribution's own header tree for that ABI.

`bin/glibc-headers` produces glibc's installed headers for the nine glibc rows of the target table, which is the libc half of a Linux sysroot for every row that says gnu rather than musl. Nine installs and seven trees, because an install is per ABI and a tree is per family: the types a program gets are decided by the size of a pointer and a long rather than by the instruction set, so x86_64, i386 and x32 are three sets of types out of the same sysdeps directories, and glibc's own headers read `__x86_64__` and `__ILP32__` and answer for all three out of one text. `make install-headers install-bootstrap-headers=yes` is the whole of the work, which is a minute and a half per row instead of the twenty minutes a build of the library would take, and the script runs three rows at a time.

The split is the same one rule `bin/kernel-headers` uses: a header every family installs with identical contents goes in the shared directory, and every other header goes in the directory of each family that has it. On glibc 2.44 that is 411 shared and 77 distinct files in 453 copies, 5.3 MB in total with 3.1 MB of it shared and 677 KB gzipped, against the 31 MB that nine separate installs would cost. The rule is about the whole tree rather than about `bits/`, even though `bits/` holds most of the difference, because 18 headers outside it are per architecture too: `fpu_control.h`, `ieee754.h`, `finclude/math-vector-fortran.h`, thirteen under `sys/` including `sys/io.h` and `sys/ptrace.h`, and `sys/platform/ppc.h` and `sys/platform/x86.h`.

Whether the rule is right is checked on every run rather than argued about: the shared tree plus a family's tree is put back together and held against the install of every ABI in that family with `diff -r`, so nine reassemblies check a split derived from seven. Nine of nine come out byte for byte. The check runs before the two files that get edited are edited, so what it compares is the rule's output and not ours.

Three configure cache variables are set on the way in, because glibc asks the compiler for `-fno-pic`, `-mlong-double-128` and `-mno-gnu-attribute` and clang has none of the three. Each one is named in the script with the probe it skips and why the answer is what it is. That all three are questions about building the library, and that a header install compiles nothing, is an argument rather than a measurement, so here is the measurement: seven of the nine rows were installed a second time with Ubuntu's own cross gcc for that architecture and no overrides at all, and `diff -r` between the two trees is empty for x86_64, x32, aarch64, arm, riscv64, powerpc64 and s390x.

Two files in the tree are not glibc's text as glibc wrote it, and the manifest's source column says so on both, with `-patched` and `-stubs-prologue` after the version. `features.h` loses its `#define __GLIBC_MINOR__`, because tamnd/rucc#928 has the compiler define that one from the target, which is what lets one tree serve every 2.x release and is what zig does to the same line. `gnu/stubs.h` is glibc's own prologue with nothing appended, because the real file lists the functions that exist and fail with `ENOSYS` and that list comes out of a built library rather than out of the source, while `features.h` includes the file unconditionally, so a tree without one compiles nothing at all. What the empty list costs, and what closing it would take, is written down in tamnd/rucc#941.

It has its own record rather than a sysroot manifest, for the reason the kernel tree has one: a sysroot manifest names the target it was produced for and this tree is every glibc target's. The record is 866 lines and 90666 bytes. Two different machines have produced it by hand, under different cache directories and different checkout paths, and the two records are the same file, which is the check `bin/glibc-headers --check` does and what the new nightly job does on an x86-64 host and an aarch64 host. A configure script run nine times is the classic way for a fact about the build machine to reach the output, so this is the producer where that criterion earns the most.

What it finds today: a program using stdio, stdlib, string, pthread, `sys/quota.h`, `net/ethernet.h`, `sys/ioctl.h` and `linux/version.h` compiles for all nine rows with every header coming from this tree and the kernel tree and none from the machine, in the search order the compiler uses, with `__GLIBC_MINOR__` arriving from the command line.

**One x86 header tree really does serve x86_64, i386 and x32, and the nine installs are what proves it rather than what ships.** The three installs are byte identical to each other, `diff -r` over each of the pairs is empty, so there is one text and three sets of types out of it. `bits/wordsize.h` reads `__x86_64__` and `__ILP32__` and answers 64, 32 and 32 from the same file, which is what compiling for the three ABIs against the one tree prints back. riscv defines `__WORDSIZE` as `__riscv_xlen`, the compiler's own macro, so that family would serve a 32-bit port without a line changing. So the tree is split over the seven families `rucc_sysroot::Sysroot::header_family` names, which is what the compiler searches for, and a family whose ABIs disagreed would be a failure with the differing files named rather than a tree that quietly serves two of three wrong.

**zig cc adds an argument to every command and then warns that it is unused, which breaks any probe that uses -Werror.** It passes `-c` to clang itself, so a command that was `-Werror -S` gets both, clang reports `-c` as an unused command line argument, `-Werror` turns that into an error, and the compile fails with nothing said about the program. glibc's configure probes the alias attribute exactly that way, so the first thing this compiler says about glibc 2.44 is that it has no working alias attribute, about a compiler whose alias attribute works. `-Wno-unused-command-line-argument` in the wrapper is the fix and it costs nothing, but the shape is worth keeping in mind, because a driver that edits the command line can turn a correct probe into a wrong answer and every autoconf script in the world is probes.

**Two of the nine rows have no Debian packaged cross gcc to check them against, and neither gap is the one you would guess.** Ubuntu 24.04's `i686-linux-gnu-gcc` defines `__CET__` as 3 with no flags given, and glibc 2.44's configure then stops with "CET is only supported on x86_64 or x32", so the row a second opinion would be most useful on is the row that cannot have one. loongarch64 has no cross gcc in the archive at all, which is the newest architecture in the table and the plainest case for why this repository exists: comparing against a per target gcc needs somebody to have packaged one first.

`bin/kernel-headers` produces the Linux uapi header tree, which is the half of a Linux sysroot no libc provides. 31 of glibc's installed headers include `<asm/...>`, `<asm-generic/...>` or `<linux/...>` and 3 of musl's do, so this is not an extra for programs that make system calls directly: the musl sysroot this repository has been producing since August cannot compile its own `sys/soundcard.h` without it. `make headers_install` out of a pinned Linux source is the supported way to get these and the only reproducible one, because copying `include/uapi` out of the source tree skips the pass that removes the kernel's own `__KERNEL__` sections from every file.

`sysroots/manifest` gains a linux 6.19 row beside the musl and glibc ones. The release is the one zig 0.16 carries, which is not a guess: the `linux/version.h` in its bundled tree says `LINUX_VERSION_CODE 398080`, and that is 6.19.0. Pinning the same one is the same argument as pinning musl 1.2.5, which is that a difference between our tree and zig's `any-linux-any` is then a difference in how it was produced rather than in what was produced. The licence column says `gpl-2.0-with-linux-syscall-note`, spelled the way `rucc-sysroot`'s manifest format spells it, and the note is the whole reason a program that is not GPL may use these headers to make a system call.

One tree for the whole target table rather than one per target, and one rule for the whole tree: a header every architecture installs with identical contents goes in the shared directory, and every other header goes in the directory of each architecture that has it, which the compiler searches first. On linux 6.19 that comes out as 970 shared headers and 333 per architecture copies, 9.1 MB against 2.2 MB, so the alternative of a private copy per row of the table would cost nine megabytes a row for files that are identical in every one of them. Zig splits its bundled copy the same way.

The rule is about the whole tree rather than about `asm/`, even though `asm/` is where almost all of the difference is, because three headers outside it are installed for some architectures and not for others: `linux/a.out.h` for x86 alone, `linux/kvm.h` everywhere except arm, which lost its KVM port, and `linux/kvm_para.h` everywhere except riscv. Those three are named in the script, and a fourth one is a failure with the path in the message rather than a tree nobody looked at. A rule with an exception in it is a rule somebody has to maintain, and one rule covers both kinds of difference, contents and presence.

The whole table is produced at once and `--force` is how it is produced again, because which files are shared is a fact about the set of architectures rather than about any one of them. A tree produced for two architectures and then extended with a third would hold the first two's private copies of files the third agrees with, which is a tree whose contents depend on the order somebody ran the script in.

It has its own record rather than a sysroot manifest, with the same four columns and a header that names the kernel release. A sysroot manifest names the target it was produced for, and this tree has no target: it is the same text for every Linux row, which is the entire reason it is not under one of them. The record is 1305 lines and the tree is 11.4 MB, 1.8 MB of the shared part and 258 KB of the seven architecture directories under `gzip -9`, which is the measurement section 13.1 of the compiler's distribution document now carries instead of an estimate.

The nightly run produces it on an x86-64 host and on an aarch64 host and requires the two records to be the same file, which is the reproducibility criterion of tamnd/rucc#619 applied to this half of a sysroot. Nothing is cached in that job, because a cache hit would skip the work and then compare two copies of a file that came from the same run. It is one of the jobs that fail the run: a header tree that came out different on two hosts is a bug in how it is produced. Two machines running the same distribution have already been held against each other by hand and the 174051 byte record came out identical, which is the weaker half of the claim, since what the nightly adds is a second architecture rather than a second machine.

**The Linux uapi headers cannot be unpacked on a default macOS filesystem, and zig 0.16 ships without the eight headers that collide.** Eight pairs of them differ only in case, all in netfilter, where the lowercase name is an iptables match and the uppercase one is the target of the same name: `xt_connmark.h` and `xt_CONNMARK.h`, and the same for `xt_dscp.h`, `xt_mark.h`, `xt_rateest.h`, `xt_tcpmss.h`, `ipt_ecn.h`, `ipt_ttl.h` and `ip6t_hl.h`. Each uppercase file is a three line wrapper that includes its lowercase twin, so what a missing one costs is the file and not any definition. Unpacking such a tree on a case insensitive volume keeps one of each pair and gives it the other's contents, and `tar` says nothing. The pinned zig tarball is missing all eight uppercase files and has all eight lowercase ones, on a Linux box as much as on this laptop, so `zig cc` for any Linux target fails on a program that includes `<linux/netfilter/xt_CONNMARK.h>`, and iptables includes it. `bin/kernel-headers` tests the filesystem before it downloads anything and refuses, which is why producing this tree is a Linux job and why there is no mac row in the nightly matrix for it.

What it finds today, with the compiler built from the branch that searches these directories: a program including `<linux/version.h>`, `<asm/unistd.h>`, `<sys/ioctl.h>`, `<net/ethernet.h>` and `<sys/quota.h>` compiles for x86_64-linux-musl with every header coming from this repository's output and none from the machine, the search order the compiler reports is the libc's two directories and then the kernel's two, and moving the tree out of the cache makes `sys/soundcard.h` fail. The executing corpus still passes with `--cc rucc`, six rows run and none failed, so the two new directories cost nothing that was already working.

`bin/abilist` extracts glibc's abilist files from a pinned glibc source, one per architecture, into the cache. An abilist is glibc's own record of which symbol it exports at which version node, and it is the description the compiler writes its glibc stubs from, so this is the data behind `cargo xtask real-libc` in tamnd/rucc: write a stub from the description, read the real `libc.so.6` on the machine with the same `readelf`, and require the real library's symbols to be a superset of ours at the same versions. `spec/cross-compile/09-libc-stubs.md` section 9.8 calls that the highest value test in the document, and it is the only one of the three that can tell a description which disagrees with reality from one that agrees with itself.

The fetch is here and the comparison is there, which is the same split `bin/sysroot` and `rucc-sysroot` have. A compiler checkout should not be downloading a libc to run its own tests, and nothing is copied into this repository either: an abilist is part of glibc and carries glibc's licence, so fetching one into the cache against a reviewed hash avoids a question that a checked in copy would raise.

`sysroots/manifest` gains a glibc 2.44 row beside the musl one, with its licence and its hash, because a libc source belongs in the table of libc sources whatever is taken out of it, and M9.5 will build a sysroot from that same row. The newest release was pinned deliberately rather than the one the oldest machine here has: a description names symbols up to the version it came from, the comparison drops every node above whatever the machine's own libc has, and a newer description therefore covers every machine an older one covers and costs nothing.

The path to each architecture's abilist is written out rather than derived, because glibc's source tree sorts by kernel and then by however each port arranged itself, and there is no rule that turns `powerpc64` into `powerpc/powerpc64/le`. Eight architectures have a row, the names being the ones the compiler uses for itself so that the comparison can look up the machine it is running on. The one row of the targets table with nothing here is `x86_64-linux-gnux32`, which shares an architecture name with x86_64 and so cannot be told apart by that key. The members are also named in full to `tar` rather than matched with a pattern, because GNU tar needs `--wildcards` for a pattern and the tar on a mac has no such flag, and naming them means a file that moved in a new glibc fails with the path in the message instead of quietly extracting nothing.

The nightly run does the comparison on both host architectures, so it is two real libcs rather than one. It is in the nightly rather than in the gate because it builds two of the compiler's crates, and the gate here is about the pinned reference toolchain and builds none of it: a morning when the compiler's main branch does not build should be a red nightly and a green gate. It is one of the two jobs that fail the run, because a symbol we promise that glibc does not have is a bug in the compiler or in the pin rather than news about the outside world.

`bin/run-corpus --cc rucc` builds the executing corpus with rucc instead of the reference and runs it the same way, against the same expected transcripts. `bin/rucc-cc` is the compiler side of it and the mirror of `bin/reference-cc`: it checks the tuple against the table, it wants `RUCC` pointing at a compiler and a sysroot already produced for the row, and then it hands rucc one cache directory rather than a path per directory. That works because `rucc-sysroot`'s layout and what `bin/sysroot` writes are the same layout under the same name, which is the exit criterion of the sysroot half of tamnd/rucc#619, and this is the run that checks it rather than asserting it.

The two scripts know nothing about each other on purpose. The reference side does not know rucc exists and the rucc side does not know the reference exists, so a comparison that uses both is comparing two independent answers instead of one answer with itself, and the reference stays the default because a transcript this repository records has to come from something other than the compiler under test.

A static binary for this machine's architecture and kernel now runs on hardware rather than under the table's emulator, and that is what makes any of this runnable today. A static binary carries its libc and the kernel does not care which one it was, so x86_64-linux-musl on an x86-64 Linux box was being handed to qemu for no reason except that the tuple was not spelled the same as the machine. Nothing else is assumed: i686 on x86-64 still goes through qemu-i386 even though the kernel would take it. `bin/run-abi-signatures` gets the same rule, because the two runners covering the same rows for the same reasons is a property worth keeping and a target that falls out of one of them is hard to notice.

Two skip reasons are about rucc rather than about this machine, and they are printed before the emulator question because they are true on every machine: a row nobody has run `bin/sysroot` for has nothing to compile against, and a row whose architecture has no back end is a row the compiler says no to itself, which today is every row that is not x86-64. A missing back end reading as a missing qemu is how somebody spends an afternoon installing an emulator that was never the problem.

What it finds today is that all three sources of the executing corpus pass for x86_64-linux-musl at `-O0` and at `-O2`, on hardware, with the headers, the start files, the libc and the loader all coming from the sysroot this repository produced and nothing coming from the machine.

`bin/lint` finds the scripts it checks instead of listing them, which it does by looking for the shebang. The list had already drifted past two scripts, and what the list is used for is the check that every script is executable, so the scripts it forgets are exactly the ones that check cannot catch.

`bin/run-abi-signatures` builds the compiler's signature corpus with the reference on both sides and runs it, on every row that has a way to run a binary, and the gate runs it beside the executing corpus. It is the control build of the four the differential harness in tamnd/rucc does, not the differential, because the other three need rucc to emit code for the target and today it emits code for one of the forty two. Running the control on its own is worth the minutes for two separate reasons.

The corpus is generated, and a generated program is a program nobody read. Compiling it for every row catches the shapes the reference rejects and `bin/compile-abi-signatures` already does that. Running it catches the ones the reference accepts and then gets wrong, or that the corpus is wrong about: a value checked against the type it was written as rather than the type it was promoted to, an initializer that does not match its check, a `long double` whose bit pattern is not the same on two architectures. Those are corpus bugs, they compile clean everywhere, and they are far cheaper to find here than inside a differential where the answer is supposed to say something about the compiler.

The other reason is the divergence list. An emulated pass is worth what the emulator is worth, and the only way to find that out is to run a program whose answer is known in advance on it, many times, on each architecture. This is that program. Every instruction in the binary came from the reference compiler, so a crash is qemu and cannot be anything else, and the count of crashes retried is printed at the end rather than swallowed so the rate can be read off the log. The retry limit is three and a wrong value is believed the first time, which is the same rule the compiler's own harness uses.

It skips the same rows `bin/run-corpus` skips, for the same reasons and on purpose: the glibc rows link against a loader that is not on this disk, the android rows have no bionic here, and the Darwin and Windows rows need a different kind of emulator than qemu user mode. Two runners that cover the same set are two runners a target cannot quietly fall out of one of.

`bin/compile-abi-signatures` compiles the compiler's generated signature corpus against the reference, for every row of the table, and the gate runs it beside the layout corpus. That corpus is written by `cargo xtask abi-signatures` in tamnd/rucc, and it is one program in four files whose two halves are meant to be compiled by different compilers and linked together, so that an argument put in the wrong register has somewhere to show up. Running it that way needs a back end and a way to execute the result, which the compiler repository has for one target. What happens here is the part that does not need either: both halves are compiled for all thirty nine spellable rows, and the answer is whether the corpus is C the reference accepts everywhere.

That is a smaller claim than the differential run makes and it covers thirty nine times as many targets, which is the trade worth making at this stage. The corpus is generated from a grammar that will keep growing, variadic signatures next, and a shape that is fine on x86-64 and a constraint violation on s390x should be found the day it is added rather than the day somebody writes an s390x back end. `report.c` is left out: it is the one file of the four that includes a libc header, it is always built by the reference compiler anyway, and asking a freestanding row for `stdio.h` would fail for a reason that has nothing to do with the corpus. The other three include nothing but each other, which is why they compile for every row the same way.

`bin/compile-abi-corpus` compiles the compiler's generated record layout corpus against the reference, and the gate runs it on every commit. That corpus is written by `cargo xtask abi-corpus` in tamnd/rucc, one C file per target named for the target, and every line in it is a `_Static_assert` about a size, an alignment or a member offset that came out of `rucc_types::layout_record`. Compiling it here is what turns those assertions into a comparison, because the reference either agrees, in which case the file compiles, or disagrees, in which case the assertion that failed names the record and the number.

It is a second script rather than a flag on `bin/compile-corpus` because the two are not the same test. That one takes C written by hand in this repository and compiles it for every row of the table, so a failure means the corpus needs fixing. This one takes C the compiler produced and compiles it for the target it names, so a failure means the compiler needs fixing. A file whose target has no spelling for the current reference is skipped and counted rather than compiled against a neighbour, and the count is printed, because a corpus that quietly stopped checking half its targets looks exactly like one that passes.

The job checks the compiler out at its default branch rather than at a pin, which is the only way it can be a check at all: a pin would keep the build green while checking last month's numbers. The nightly `second-opinion` job compiles the same corpus against cross gcc, which is the run that would catch rucc having been made to agree with clang about something gcc does differently.

All forty two rows have a file. Fifteen did at first, because laying a record out in the compiler needed a three field triple while `rucc-abi` described all forty two, and closing that in tamnd/rucc turned the gap into three skipped rows here instead: `arm64ec-windows-msvc`, `wasm32-wasip3` and `x86_64-illumos` have no zig spelling, so this job names them and counts them rather than compiling them against a neighbour. The first run over the new rows found one disagreement, `long double` on wasm32, which is a sixteen byte IEEE quad and which `rucc-abi` had grouped in with the thirty two bit machines and given a `double`. `facts/wasm32-none.facts` here had said quad and sixteen since the day it was written, so the fact was on disk and the compiler contradicted it, which is exactly what this job is for.

`bin/sysroot` produces a musl sysroot for a target and writes the manifest that says what went into it. `sysroots/manifest` pins the musl source by version, licence and sha256, the same shape `toolchains/manifest` uses, and the version is 1.2.5 because that is what Zig 0.16 carries and comparing against a different one would compare two things at once. The build uses the pinned zig as the cross compiler rather than whatever `cc` the machine has, for the same reason.

The layout it produces is the one `rucc-sysroot` in the compiler repository reads: `include/<arch>` for the headers that differ by architecture, `include/generic` for the copy every architecture shares, `lib` for the start files and the archives, and `manifest` at the top. musl installs one flat include tree with the architecture specific files in `bits/`, so the split is a move of that one directory.

This is the exit criterion of the sysroot half of tamnd/rucc#619, and running it found the thing it was built to find. All four musl targets were produced on a macOS arm64 laptop and on a Linux x86-64 box, and the first comparison had 219 identical headers and six different compiled artifacts. The difference was `DW_AT_comp_dir`: clang writes the working directory into every object, including the ones assembled from `.s` files, and the two machines have different home directories. With `-fdebug-compilation-dir=.` and `-ffile-prefix-map` the four targets reproduce byte for byte, manifest and contents, and `bin/sysroot --check` is the comparison as a command.

The repository stops being a Rust workspace and becomes what its name says: the toolchains, the environment and the C corpus that the compiler is compared against.

`crates/`, `xtask/`, `spec/`, `docs/`, `Cargo.toml`, `Cargo.lock` and the release workflow are gone. `rucc-tuple` and the target table moved to the compiler repository, where they belong, because they are compiler code and splitting the compiler across two repositories bought nothing except a version number between a crate and its only caller. The specification moved with them to `spec/cross-compile/`. Anything published in the 0.1.0 tag of this repository is superseded by that move, and the tag stays where it is as a record of where the code was.

What replaces it has no build system and no dependencies. `toolchains/manifest` pins the reference compilers by version and sha256, `toolchains/install` fetches and verifies them, and `targets` is the table of forty two targets with the spelling each reference wants for each one. Every zig spelling in that table was verified by running the compiler rather than read from documentation, which is how four spellings that do not exist and one that is not the obvious guess were found.

The corpus is in three parts. `corpus/layout/` is `_Static_assert` over sizes, alignments and signedness, with the reason for each number written beside it, and it compiles for every target without needing a machine to run on. `corpus/abi/` and `corpus/exec/` are programs that print values rather than sizes, so one expected transcript serves every target and a divergence is a miscounted register rather than a layout difference. `facts/` is the preprocessor's answer for each target, recorded, so a reference toolchain that changes its mind shows up as a diff instead of as a mystery.

Four drivers run all of it: `bin/facts`, `bin/compile-corpus`, `bin/run-corpus` and `bin/lint`. They are POSIX sh and checked with shellcheck, on the reasoning that a repository whose job is to be the thing you trust when the compiler under test is suspect should not have a toolchain of its own to be suspicious of.

The corpus found four bugs in its own assertions before it found anything else, which is the part worth recording. mingw aligns `double` and `long long` to eight bytes rather than following the System V i386 psABI. s390x caps scalar alignment at eight, so a sixteen byte `long double` and `__int128` are both eight aligned. wasm32 and the x32 ABI both have `__int128` with four byte pointers, so an assertion that tied the two together was simply wrong. It then found two in the compiler: s390x `char` is unsigned and `rucc-tuple` said signed, and `long double` on mingw is x87 extended while `rucc-abi` keyed the rule on the operating system alone and gave every Windows target the MSVC answer.

## 0.1.0

The first release, and the whole of milestone M0: the target model. Superseded by the move described above, and kept here because the tag exists.

`rucc-tuple` replaced the three field triple with a ten field tuple. The fields are the architecture, the baseline within it, the byte order, the data model, the operating system, the OS version, the environment, the environment version, the float ABI and the object format. The membership rule is that a fact is in the tuple if it changes how a function is called or how a struct is laid out, and it is a flag otherwise. That rule is what makes a tuple usable as a cache key, which is what the sysroot cache and the stub generator both need.

Three things the old model got wrong were fixed by having the fields at all. The pointer width came from the data model rather than from the architecture, so a 64-bit Windows target correctly had 64-bit pointers and a 32-bit `long`, and `x86_64-linux-gnux32` correctly had 32-bit pointers on a 64-bit machine. The byte order was a field rather than a constant, so s390x was big-endian and `powerpc64le` and `aarch64_be` were spellable. The address width was exposed separately from the pointer width.

The parser discarded nothing. The old one had a catch-all arm that skipped components it did not recognize, so `x86_64-linux-gnu.2.28` parsed as `x86_64-linux-gnu` and the pinned glibc version vanished with no diagnostic. Every component was either understood or named in an error, and combinations that do not describe a machine, such as `x86_64-macos-musl`, were refused with the component that was wrong.
